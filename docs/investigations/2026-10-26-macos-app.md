# A proper macOS app: investigation

Date: 2026-10-26

## Question

What does noido need on macOS to be a real app (one that can be chosen as
the default PDF viewer, not only run from a terminal), and can it be
distributed without a paid Apple developer account?

## Answer

**Yes, without an account; the account only removes a first-launch
warning.** Being the default viewer needs three things: a `noido.app`
bundle, an `Info.plist` that declares PDFs, and code that accepts files
from Finder. The last one is the real work: Finder sends files as an Apple
Event, which winit drops, so noido has to add a handler to winit's own app
delegate. Distribution: a Homebrew cask that installs both the `.app` and
the `noido` command, alongside the formula from the release setup (see
`2026-10-26-versioning-and-releases.md`). Everything here needs a Mac to
check.

## What being the default PDF viewer needs

1. **An app bundle.** Finder and Launch Services only offer apps, never
   bare binaries:

   ```
   noido.app/Contents/Info.plist
   noido.app/Contents/MacOS/noido
   noido.app/Contents/Resources/noido.icns
   ```

   `Info.plist`: a bundle identifier (e.g. `io.github.rikardg.noido`) and
   `CFBundleDocumentTypes` with `LSItemContentTypes = [com.adobe.pdf]`,
   `CFBundleTypeRole = Viewer`, `LSHandlerRank = Alternate`.
2. **Registration with Launch Services.** Happens on its own when the
   bundle is in `/Applications` or `~/Applications`, or launched once;
   `lsregister` forces it. Then Finder's *Get Info → Open with → Change
   All…* offers noido. Choosing it is the user's step. An app may also ask
   to become the default (`NSWorkspace setDefaultApplication…`, macOS 12+;
   the system asks the user to confirm), e.g. behind a button; never
   silently.
3. **Accepting files from Finder.** See below. Without it noido can be
   picked as the default but starts without the document.

## Files from Finder: the open-URLs event

When Finder opens a file in an app (double-click, *Open With*,
`open -a noido file.pdf`, dropping on the Dock icon), the path doesn't
arrive in `argv`. It arrives as `application:openURLs:` on the
`NSApplicationDelegate`, at launch and while the app runs.

- **winit 0.30.13 (used by eframe 0.37) drops it.** Its docs say winit
  never registers an app delegate and that apps should register their
  own. The code does the opposite: it installs `WinitApplicationDelegate`
  in `EventLoop::new` (`platform_impl/macos/event_loop.rs:240`) and panics
  if it's replaced (`app_state.rs:182`, "tried to get a delegate that was
  not the one Winit has registered"). So noido can't install its own
  delegate.
- **What works:** add the `application:openURLs:` method to winit's
  delegate class at runtime (`class_addMethod`), early, when the app is
  about to finish launching, or the launch file's event is lost. The
  handler queues the paths and wakes egui; the app drains the queue each
  frame (e.g. in eframe's `raw_input_hook`) and opens through the same
  path as `argv`, the single-instance IPC and drag-and-drop.
- **References, no ready-made crate for egui:**
  - `bevy_macos_open_files` does this for Bevy; tied to Bevy, but the core
    is small. Relies on winit's private class name.
  - GridCraft PR #18: an egui app doing the same, with `raw_input_hook`.
  - winit #1751 (double-click opening a file, open for years) and #4260
    (app delegates). winit 0.31 is expected to let apps register their own
    delegate again, which simplifies this once eframe moves.
- **Where the code goes:** it needs `unsafe` (`objc2`), and the workspace
  has `unsafe_code = "forbid"`, which `#[allow]` can't lift. So a small
  macOS-only crate (say `noido-macos`) that doesn't take the workspace
  lints, or declares `unsafe_code = "deny"` and allows it at the few
  places needed. `objc2`, `objc2-foundation`, `objc2-app-kit` under
  `[target.'cfg(target_os = "macos")'.dependencies]`, at the versions
  winit 0.30 uses (the 0.5 series). Roughly 50–100 lines.
- **To check on a Mac:** whether it works only from a bundle (winit's own
  example says it "might"); that the launch file isn't lost; that a file
  opened while noido runs goes to the right window; re-check on every
  winit upgrade.

## Signing and Gatekeeper without an account

- **Ad-hoc signing is free and automatic.** Apple Silicon won't run
  unsigned arm64 code; the Rust linker signs ad hoc, and `codesign -s -`
  re-signs a bundle.
- **Gatekeeper checks quarantined files.** Browsers and most download
  tools set the quarantine flag. A quarantined app that isn't notarized is
  blocked on first launch. On recent macOS (Sequoia on) Control-click →
  Open no longer bypasses it: the user tries to open it, then *System
  Settings → Privacy & Security → Open Anyway*, or runs
  `xattr -dr com.apple.quarantine noido.app`. Once per download.
- **Not quarantined:** apps built locally, and (as far as known) binaries
  installed by a Homebrew formula. Casks are quarantined.
- **A Developer ID ($99/year)** buys signing and notarization: no warning,
  and eligibility for the official homebrew/cask. Nothing functional.
  Homebrew has been tightening rules on unsigned casks and has deprecated
  `--no-quarantine`; check how far that reaches into third-party taps
  before relying on an unsigned cask.

## Distribution channels

All three can coexist; the release job feeds the tap and the GitHub
release alike.

| Channel | Updates | Gatekeeper |
| --- | --- | --- |
| Formula + `noido --install` (builds `~/Applications/noido.app` around a copy of the binary, signs ad hoc, registers) | `brew upgrade`, then the bundle's copy is stale until `--install` runs again (noido could notice at startup) | No quarantine, as far as known |
| Cask | `brew upgrade` replaces the `.app` (casks marked `auto_updates true` are skipped without `--greedy`; noido wouldn't set it) | Quarantined; probably "Open Anyway" again after each upgrade, since each download is quarantined again. Not verified |
| `.dmg` from GitHub releases | None, unless noido checks itself | "Open Anyway" on first launch |

- **A cask can install the command too:**

  ```ruby
  cask "noido" do
    version "0.2.0"
    sha256 "…"
    url "https://github.com/rikardg/noido/releases/download/v#{version}/noido-#{version}-macos-arm64.dmg"
    name "noido"
    homepage "https://github.com/rikardg/noido"

    app "noido.app"
    binary "#{appdir}/noido.app/Contents/MacOS/noido"
  end
  ```

  `binary` symlinks into Homebrew's `bin` (`/opt/homebrew/bin` on Apple
  Silicon, `/usr/local/bin` on Intel), as VS Code's cask does for `code`.
  App and command are the same file. Whether a symlink straight to the
  bundle's executable behaves, or a small wrapper script is better, needs a
  Mac. A terminal launch while noido runs hands the file to the running
  window through the single-instance IPC.
- **Formula and cask collide:** both want `bin/noido`, so a user can't
  have both; same-named formula and cask also make `brew install noido`
  pick the formula with a warning (name the cask `noido-app`, or use
  `--cask`).
- **Two bundles:** a cask's `/Applications/noido.app` and an `--install`
  one in `~/Applications` would share a bundle ID; Launch Services picks
  one. `--install` should notice `/Applications/noido.app` and say so.
- **So:** on macOS the cask is the main channel (app plus command); the
  formula plus `--install` is a fallback without Gatekeeper prompts, and
  the formula mainly serves Linuxbrew.
- **Self-update:** Sparkle is the usual framework (its own signing key, no
  Apple account; Objective-C). Lighter: noido checks the GitHub releases
  API and says a new version exists; that serves every channel.
- **Building the bundle and `.dmg`:** cargo-packager (supports file
  associations in its config), run as a custom job in the dist workflow.

## Windows, for comparison

Default apps come from registry entries under `Software\Classes` plus the
user's choice in Settings → Default apps; `--install` could write them per
user. Unsigned downloads get a SmartScreen warning, the same kind of hurdle
as Gatekeeper.
